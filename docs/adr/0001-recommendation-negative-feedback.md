# ADR 0001: レコメンドの負例をプロファイルベクトルの補正で扱う

- ステータス: 採用
- 日付: 2026-08-08
- 関連: [#336](https://github.com/Tomodo1773/podcast-queue/issues/336)
- 対象コード: `lib/recommendation/profile.ts`, `app/api/cron/recommend/route.ts`

## 背景

レコメンドは、視聴中・視聴済みポッドキャストのembedding平均（興味プロファイル）と、
YouTube新着動画のembeddingとの cosine 類似度でスコアリングし、閾値を超えた上位3件を
LINE通知している。

issue #336 で、通知カードの「興味なし」ボタンから**負例**を集められるようにした。
この負例をスコアリングにどう反映するかを決める必要があり、複数案を検討した。
本ADRはその検討過程と結論を残すもの。

決定に効いた前提:

- **負例のサンプル数が極端に少ない。** 正例は視聴履歴から自動的に数十〜数百件たまるが、
  負例は「ユーザーがボタンを押した数件」しかない。個人開発アプリなので今後も桁は変わらない
- **上流で候補が絞られている。** 新着のみ（1日数本）→ 閾値超え → 上位3件。母数が小さい
- **失敗の方向が非対称。** 「効かなさすぎ」は通知が来るので気づける。「効きすぎ」は
  無通知になり「新着がなかった」と区別がつかないので気づけない
- **閾値チューニングが進行中。** `RECOMMEND_SCORE_THRESHOLD` はログを見ながら調整している段階で、
  確定値ではない

## 検討した3案

### A. 閾値による除外

負例のいずれかとの類似度が閾値を超えた候補を、通知対象から落とす。
issue #336 の文面（「強く類似する候補を通知対象から除外する」）が指していた案。

利点:

- issue の文面に忠実で、実装が最小（フィルタ1本）
- パラメータが1つ（除外閾値）だけで、既存の `RECOMMEND_SCORE_THRESHOLD` と直交する。
  通知が来ないときに、どちらのパラメータが原因かを切り分けられる
- 「なぜ落ちたか」がログに書ける（`rejected by dislike(sim=0.88)`）。
  閾値チューニング中の可観測性が高い
- 負例が少数で不安定な状況でも、影響が「その負例に酷似した候補」に局所化される

懸念:

- **閾値の崖がある。** 上流で既に絞られた候補をさらに削るため、通知が枯れうる。
  特に同一チャンネルの動画同士は語彙・話者・番組名が共通し cosine が 0.8 を超えるので、
  「この話題は要らない」のつもりが実効的にチャンネルまるごとミュートになりかねない
- 前提に挙げた非対称性により、**この失敗には気づけない**
- プロファイル類似度がいくら高くても、負例に似ていれば問答無用で落ちる
- 閾値を決めるためのデータが手元にない。決めるには測定用のドライラン機構が要る

### B. 候補ごとの減点

```
score = cos(c, プロファイル) − w · max_i cos(c, 負例_i)
```

利点:

- **連続的で崖がない。** 効きすぎても「スコアが下がる」で済み、通知が突然止まらない
- **プロファイル類似度で挽回できる。** 負例に似ていても正例により似ていれば生き残る。
  案Aにはできない挙動で、これは案Aより構造的に優れている点

懸念:

- パラメータが `w` と `RECOMMEND_SCORE_THRESHOLD` の2つになり、両者が相互作用する。
  減点後のスコアは全体的に下がるので閾値も動かす必要があり、通知が来ないときに
  「w が強すぎるのか閾値が高すぎるのか」を切り分けられない
- `w` を決めるためのデータも手元にない（案Aと同様）
- `max` による集約は、単一の負例に結果が支配される。負例が数件しかない前提では、
  誤タップ1件が空間内に恒久的なホットスポットを作る
- 候補ごとに負例全件とのループが必要で、負例embedding全件をJS側に転送することになる

### C. プロファイルベクトルの補正（Rocchio方式）

```
profile = normalize(mean(正例)) − γ · normalize(mean(負例))
```

スコアリング以降の処理は変えず、プロファイルを作る時点で負例を織り込む。
情報検索の適合性フィードバックの古典的手法（Rocchio 1971）。

利点:

- **案Bの利点（崖がない・プロファイル類似度で挽回できる）をそのまま持つ**（後述の通り
  案Bと同じ族のため）
- 既に `get_profile_embedding` RPC でプロファイルを組み立てる構造があるので、
  その隣に負例側を足すだけで収まる。**cron のスコアリング以降は1行も変わらない**
- 負例の平均は `avg()` で SQL 側が計算できるため、転送はベクトル1本で済む
- 合成が純粋関数1つに閉じるので、issue の完了条件「選定ロジックの正常系テスト」が
  素直に乗る
- 崖がないので、案A・案Bで必要だった測定用ドライランなしに投入できる

懸念:

- プロファイルの向きが変わるため、スコアの絶対値がずれる。
  `RECOMMEND_SCORE_THRESHOLD` の再調整が一度必要（詳細は後述）
- 案Aが持っていた「特定シリーズを確実にブロックする」力はない
- 正例・負例のノルムが揃わない問題への対処が必要（後述）

## 案Bと案Cの関係

検討の過程で、この2案が**数学的に同じ族**であることが分かった。判断材料として重要なので記録する。

embedding は単位ベクトル（Gemini API 側で正規化される。`lib/gemini/generate-embedding.ts` 参照）。
負例を d_1..d_N、その平均を m、n̂ = m/‖m‖ とすると

```
cos(c, n̂) = c·m / ‖m‖ = ( 1/‖m‖ ) · mean_i cos(c, d_i)
```

したがって案Cのスコアは

```
score = cos(c, p̂ − γn̂)
      = [ cos(c, p̂) − γ · cos(c, n̂) ] / ‖p̂ − γn̂‖
      = [ cos(c, p̂) − (γ/‖m‖) · mean_i cos(c, d_i) ] / D
```

`‖m‖` も `D = ‖p̂ − γn̂‖` も候補 c に依存しないユーザーごとの定数なので、
**候補間の順位付けは `cos(c,p̂) − w_eff · mean_i cos(c,d_i)`**（w_eff = γ/‖m‖）。

つまり案Cは「**mean で集約する減点方式を、プロファイル側に畳み込んだもの**」。
両者の実質的な違いは次の2点に絞られる。

| | 案B | 案C |
|---|---|---|
| 集約 | `max`（最も近い負例） | `mean`（負例の平均） |
| 計算場所 | 候補ごとのループ | プロファイル合成時（SQLで平均） |

集約の違いは挙動に効く。`max_i cos(c, d_i)` は負例集合に要素を足すと単調非減少するため、
負例がたまるほど減点が強くなる（パラメータを変えていなくても効きが変わる）。
案Cの減点量 `γ · cos(c, n̂)` は cos の値域から ±γ に収まり、件数によらず上限が動かない。
一方で `max` のほうが「特定の1本に酷似したもの」への反応は鋭い。

## 決定に至った経緯

1. **当初は案Aを推した。** パラメータが直交していてチューニング中の切り分けがしやすいこと、
   ログで因果が読めること、負例が少数で不安定なので影響を局所化したいことが理由
2. **「除外だとレコメンドが来なくなるのでは」という指摘を受けた。** これは正しく、
   提示していた閾値0.8には根拠がなかった。同一チャンネルの動画は cosine 0.8 を
   普通に超えるため、実効的なチャンネルミュートになりうる。加えて前提の非対称性により
   この失敗は観測できない
3. **この論点では案Bのほうが構造的に強いと認めた。** ただし `w` を決めるデータも
   ないため、測定フェーズはパラメータ1つの案Aで回し、データが出てから案Bに切り替える
   —— という折衷を提示した（案Aにドライランを付ける形）
4. **案Cが提示された。** 「見た動画のベクトルを全部足して、見たくないものは引いて平均」
   という発想で、これが Rocchio に相当する
5. **案Cに決定。** 案Bの利点を持ちながら既存構造に収まり、崖がないためドライランも不要。
   案A・案Bのどちらよりもコードの追加が少ない

## 決定

**案C（プロファイルベクトルの補正）を採用する。**

- γ のデフォルトは 0.25、環境変数 `RECOMMEND_DISLIKE_WEIGHT` で調整する
- 正例・負例の両方を正規化してから合成する
- 負例の平均は `get_dislike_embedding` RPC で DB 側が計算し、ベクトル1本だけ転送する
- 合成は純粋関数 `buildProfile()`（`lib/recommendation/profile.ts`）で行う

γ を 0.25 と小さめに置いたのは、負のフィードバックが正に比べてノイジーなため
（「この1本が嫌」なのか「この話題全部が嫌」なのか区別がつかない）。
オリジナルの Rocchio でも負例の重みは正例の1/5程度に置かれる。

## 実装上の要点: 正規化が必須

`buildProfile` は正例・負例の両方を `normalize()` してから引く。

`avg()` は要素ごとの平均なので、平均されるベクトルの向きがバラバラなほど結果のノルムが縮む。
実際には次の逆転が起きる。

- 正例: 多様な興味の動画を数十〜数百件平均 → ノルムが小さい（0.6程度）
- 負例: 似た動画を数件平均 → ノルムが大きいまま（0.9近く）

**件数が少ないほうが長くなる。** 正規化せずに引くと、数件の負例が数百件の正例を
押しのけてプロファイルの向きを乗っ取る。

`profile.test.ts` の「正例・負例のノルムの大きさに結果が左右されない」は
この性質を守るためのテスト。正規化を外すと落ちる。

## 結果として受け入れたこと

### 閾値の再調整が一度必要

分母 `D = ‖p̂ − γn̂‖` はユーザーごとの定数なので順位付けには影響しないが、
**スコアの絶対値がずれる**。γ=0.25・cos(p̂,n̂)=0.7 なら D≈0.844 になり、
負例との類似が 0.37 を下回る候補はむしろスコアが上がる。

そのため cron のログに補正なしのスコアを併記している。

```
[recommend] score=0.580 (base 0.620) タイトル
```

- `score − base` が全候補で一様 → 向きの変化によるスケールずれ。`RECOMMEND_SCORE_THRESHOLD` を調整する
- 特定候補だけ下がっている → 意図どおり効いている

分母は再正規化では消せない。cosine はスケール不変なので、`buildProfile` の戻り値を
単位ベクトルに直しても分母の効果は残る。向きの変化に由来する量であって長さの問題ではない。

### 負例0件のユーザーには影響がない

cosine はスケール不変なので `normalize(正例)` と `正例` は同じスコアを返す。
`buildProfile` は負例が null なら正規化した正例をそのまま返す。
移行の影響は「興味なし」を押したユーザーだけに閉じる。

### 負例1件目からγの強さがかかる

負例が1件のとき、負例の平均はその動画のembeddingそのもの。件数による減衰は入れていない
（パラメータを増やさないため）。初回のタップから効き始めるので、誤タップの影響は小さくない。
取り消しUIは issue #336 のスコープ外としたが、フォローアップとして残っている。

### 特定シリーズの確実なブロックはできない

案Aが持っていた力。必要になった場合、**案Cと案Aは排他ではない**ので、
プロファイル補正の上に閾値除外を重ねられる。単純なほうから始めている。

## この決定を見直す条件

運用データが出てから再検討する余地があるのは次の場合。

- **`max` 集約が必要になったとき。** 「特定の1本に酷似した動画だけを強く弾きたい」
  という要求が実際に出てきた場合。案Cの `mean` は鋭さで劣る
- **負例が想定より多くたまったとき。** 数十件を超えて多様化すると負例の平均が
  中庸なベクトルに収束し、補正が効かなくなる可能性がある。
  そのときはクラスタリングして複数の負例プロファイルを持つ、などの拡張がありうる
- **γ の調整だけでは望む挙動にならないとき。** 0.2〜0.3 を 0.05 刻みで動かしても
  「効きすぎる／効かない」が解消しない場合、集約方法かモデル自体を疑う

いずれも**ログの観測が前提**。`score` と `base` の乖離を見ずに方式を変えても、
何が改善したのか判断できない。
